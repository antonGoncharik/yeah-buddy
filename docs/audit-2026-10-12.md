## 1. Резюме

Проект зрелый и аккуратный: 128 тыс. строк TypeScript в strict-режиме, 178 `*.check.ts`, biome, чистый `tsc`, продуманный офлайн-слой (outbox, оптимистичные дни и сессии), атомарные AI-квоты, README на уровне технической документации. Линт, тесты и `tsc` проходят. Production-сборка на копии проекта собирается без ошибок.

Что можно сказать про позиционирование. «Еда + зал в одном дневнике внутри Telegram» — редкое сочетание. Рядом есть Telegram-боты с AI-подсчётом калорий (NOMS, BioTrakk, ShotMeal, ProPORTION, perek.us, «Зоя»), но без тренировок. Есть тренировочные трекеры (Hevy, Strong) без питания. Есть MacroFactor — у него адаптивные калории и теперь отдельное приложение Workouts, но он платный, без Telegram и слабый по русской базе. Сильные стороны вашего продукта: адаптивная цель по калориям с фильтрацией выбросов, карта мышц с зонами объёма и восстановлением, программы с авторасчётом рабочего веса, офлайн, режимы «тренер» и «пара».

Главные слабости:

1. **Безопасность и целостность.** Версия Next.js 16.3.4 попадает под критические advisory (в том числе RCE в `next/og ImageResponse`, а проект генерирует OG-картинки). Кэш в `localStorage` не привязан к пользователю. Очередь синхронизации может заблокироваться одной «ядовитой» операцией. Нет ни одного `error.tsx`.
2. **Комплаенс.** В проекте нет политики конфиденциальности и условий, при этом он хранит вес, обхват талии, тренировки и отправляет фото, аудио и тексты в Google Gemini.
3. **Напоминания.** Ошибка в предфильтре часовых поясов задерживает вечернее напоминание у пользователей с выбранным часом 17–20 на несколько часов. [V]
4. **Конкурентный разрыв по AI.** Бесплатные конкуренты дают десятки AI-записей в день, у вас 3 на функцию. Нет клетчатки, воды, микроэлементов, быстрого ввода только калорий, нет модели монетизации кроме донатов Stars.
5. **UX.** Экран Today перегружен на 15–30-й день, в сессии не подключена кнопка отдыха на упражнении, карта мышц показывает данные, но не ведёт к действию. Лендинг — аккуратный, но без реальных скриншотов и без политики конфиденциальности.

### P0-02. Привязать локальный кэш к пользователю — [V], M

**Факт:** `src/lib/api-cache.ts`: ключи `yb.v1:<url>` без идентификатора пользователя. `clearDiaryCache()` вызывается только при удалении аккаунта (`settings-account.tsx:55`). В `telegram-gate.tsx` после успешного `/api/auth/telegram` кэш не сверяется, а при ошибке сети используется `hasLocalDiary()`. Если на одном устройстве (общая Telegram Desktop/Web-сессия, смена аккаунта) войдёт другой пользователь, он увидит чужой дневник из `localStorage` до обновления с сервера; офлайн — без ограничений. Заодно в `outbox` могут остаться чужие операции.

**Шаги:**
1. `POST /api/auth/telegram` возвращает `{ ok: true, userId }` (внутренний uuid, не Telegram id).
2. Новый модуль `src/lib/cache-owner.ts`: `ensureCacheOwner(userId)` читает `localStorage["yb.v1:owner"]`; если отличается от `userId` — вызывает `clearDiaryCache()` (она уже чистит outbox и черновики сессий; убедись, что она удаляет **все** ключи с префиксом `yb.v1:`), затем записывает владельца.
3. Вызови `ensureCacheOwner` в `telegram-gate.tsx` после `response.ok`. Для офлайн-пути (`hasLocalDiary()`) владелец уже записан — оставь как есть.
4. `*.check.ts` с фейковым `localStorage`: смена владельца очищает кэш; тот же владелец — нет.

**Приёмка:** после входа под другим аккаунтом локальные данные прежнего недоступны, outbox пуст.

### P0-03. Очередь синхронизации: «ядовитые» операции, 401, backoff — [V для блокировки очереди, A для остального], L

**Факт [V]:** `flushOnce` в `src/lib/outbox-flush.ts` берёт `ops[0]`; при ошибке не-сети/не-401 (400, 404, 500) показывает ошибку и делает `return`, операция остаётся первой. Каждый следующий запуск упирается в неё же, поэтому одна невалидная операция блокирует синхронизацию всех последующих навсегда. 401 (истёк 7-дневный JWT при открытом Mini App) тоже останавливает очередь, а повторного запуска после переавторизации нет (`outbox-sync.tsx` слушает только `online` и `visibilitychange`). Конфликты 409 обрабатываются только для создания дня/сессии. `api-cache.ts`: записи > 180 000 символов молча не сохраняются, при переполнении квоты нет вытеснения.

**Шаги:**
1. Классифицировать ошибки: *повторяемые* (сеть, 5xx, 429), *терминальные* (4xx, кроме 401 и 409). Терминальную операцию переносить в `yb.v1:outbox:dead` (с кодом ошибки и временем), остальную очередь продолжать.
2. Экспоненциальный backoff для повторяемых (1 с → 30 с, предел), счётчик попыток.
3. После успешной переавторизации (`telegram-gate`) и при любом 401 из `mutateJson/fetchJson` — запуск `flushOutbox()`.
4. Показ «мёртвых» операций: Settings → «Данные» → «Не удалось синхронизировать: N» с кнопками «Повторить» и «Удалить». Отправка `sync_failed` в product-events (см. P1-11) и в Sentry с `op.url` без тела.
5. `api-cache.ts`: при `QuotaExceededError` вытеснять самые старые записи `yb.v1:*` по `at`, пока запись не поместится.
6. Тесты `outbox-flush.check.ts`: «ядовитая» операция не блокирует соседние; 401 останавливает и возобновляется; 5xx ретраится.

**Приёмка:** одна невалидная операция не мешает синхронизации остальных; после обновления сессии очередь уходит сама.

### P0-05. Вечернее напоминание приходит поздно при выбранном часе 17–20 — [V], M

**Факт:** `src/lib/telegram/reminder-timezones.ts` фильтрует часовые пояса через `reminderDateIfDue(clock)` с часом по умолчанию 21 (`REMINDER_HOUR`). Пользователь с `reminder_hour = 17` попадёт в выборку только когда в его поясе станет 21:00, хотя `processEveningCandidate` (reminder-run.ts) корректно считает по `candidate.reminderHour`. Аналогично midday-фильтр считает окно до 21, а не до выбранного часа.

**Шаги:**
1. В `eveningDueTimezoneKeys` проверять минимально возможный час (`clock.hour >= 17`), а точную проверку оставить на уровне кандидата. В `middayDueTimezoneKeys` использовать верхнюю границу 23.
2. Тест в `reminder-timezones.check.ts`: `reminder_hour = 17`, локальное время 18:00 → пояс в выборке; 16:59 → нет.
3. Догон (R-02, [A]): если все запуски после наступления часа упали (простой Vercel, таймаут 60 с), сводка за день D не отправится никогда. Разрешить отправку за вчера, если `reminded_on < вчера`, нет отправки за вчера и локальный час < 3; одно письмо, без дублей.
4. Взять в расчёт: на Vercel Hobby крон срабатывает «в течение часа», а не в минуту; пользователю в UI обещать «около 21:00».

**Приёмка:** тесты зелёные; пользователь с 17:00 получает сообщение в 17:xx.

## 5. P1 — ближайшие 2–4 недели

### P1-01. Идемпотентность завершения сессии и блокировка правок после неё — [A, W-001/W-002], M

### P1-02. Питание: ошибки расчёта — [V N-001, A остальное], M
